## Поведение игрока

Обновление страницы при кратком отказе API больше не удаляет локальный вход.
Ошибка сети, HTTP 408, 429 и 5xx запускают последовательные повторы с задержкой
от одной до 30 секунд. Успешная проверка возвращает игрока в его аккаунт.
HTTP 401/403 удаляет недействительную локальную сессию и останавливает её запросы.
Другие ошибки, включая ответ HTML вместо API, показываются без удаления ключа
и без бесконечных автоматических повторов.

Временная ошибка обновления профиля сохраняет уже подтверждённого игрока.
Обновление токена Supabase для того же пользователя сохраняет профиль и открытую
партию. Смена пользователя сразу скрывает предыдущий профиль; новый появляется
после проверки сервером. Выход немедленно очищает профиль и локальный ключ,
отменяет проверку и таймер, даже если сервер ещё отвечает на запрос выхода.
Поздний результат старой проверки не возвращает прежний аккаунт и не меняет
ошибку нового игрока.

Первичный вход, ручное обновление профиля, уведомления `accountChanged` и проверка
перед восстановлением Socket.IO используют один механизм чтения `/me`.
Параллельные обращения разделяют ожидающий запрос. Если изменение профиля
произошло после начала чтения, уведомления объединяются в одну последующую
проверку: новое имя или состояние аккаунта больше не теряется за старым ответом.
Выход отменяет и эту ожидавшую проверку.

Для Supabase текущий токен берётся из синхронного обработчика событий, включая
`INITIAL_SESSION` и `TOKEN_REFRESHED`; отдельное первоначальное чтение сессии
больше не конкурирует с этими событиями. Такой способ инициализации описан в
[официальной документации onAuthStateChange](https://supabase.com/docs/reference/javascript/auth-onauthstatechange).
Профиль и необходимость второго фактора по-прежнему проверяет сервер `/me`.
Проверка MFA останавливает переподключение до появления подтверждённого токена.
