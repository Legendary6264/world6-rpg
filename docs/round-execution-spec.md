# «Грани Бытия»: спецификация R01/R02 — исполнение раунда

11 октября 2026 года. Основание: [план восстановления](recovery-plan.md), ТЗ 1.1, отчёт P20, текущие `actionDeclarations.ts`, `roundTimeline.ts`, `rpgEngine.ts` и серверные маршруты. База исходников — `da6108e`; план добавлен коммитом `3eaa633`.

Документ описывает следующий блок реализации. Новые поля, маршруты и алгоритмы ниже ещё не существуют в коде. Это техническое предложение в рамках согласованной игры; неутверждённые численные/игровые правила явно оставлены решениями мастера или точками согласования. Код, GitHub, рабочий сайт и внешняя база в этой работе не изменяются.

## 1. Результат блока

Мастер закрывает сбор → рассчитывает порядок и последствия → видит изменения, незавершённую работу и вопросы → принимает решения → выполняет отдельное применение. Мир изменяется одной атомарной операцией. Повтор команды не создаёт второй раунд или расход.

В следующем сборе сохраняется фактически накопленная работа. Игрок видит собственное состояние и доступные ему последствия. Мастер по-прежнему решает отсутствие заявления и совпадающие/неформализованные события.

Этот блок не объявляет завершёнными расширенный редактор способностей, полный откат, экономику, речь по слышимости, голос или обучение. Они получают совместимые точки подключения. Неподдерживаемое действие не исчезает из раунда и не заменяется автоматическим ожиданием.

## 2. Состояния и переходы

Оставить существующий `DeclarationCollection.phase` (`open`, `closed`, `cancelled`). Не добавлять ему фиктивную фазу «исполнен» без миграции. Исполнение получает отдельную серверную запись, связанную с ID и эпохой сбора.

| Состояние | Что разрешено | Что переводит дальше |
| --- | --- | --- |
| Нет активного сбора | Просмотр, подготовка черновиков, настройка мастером. | Открытие сбора принятых героев. |
| Сбор открыт | Приватные заявления, возврат/замены согласно настройке; не исполнение. | Закрытие мастером повышает эпоху. |
| Сбор закрыт, исполнения нет | Временной прогноз, расчёт последствий, явные решения мастера. | Применение рассчитанного результата либо повторное открытие. |
| Результат рассчитан | Это предпросмотр, а не новая игровая фаза: мир и часы прежние. | Применение, пересчёт или любое изменение базы, делающее его устаревшим. |
| Сбор исполнен | Просмотр результата/личных последствий; архивирование исполненного сбора. | Новый сбор; изменение прежних заявлений только через будущую переигровку R04. |
| Сбор отменён/архивирован без исполнения | История объясняет, что раунд не произошёл. | Новый сбор; нельзя использовать старый предпросмотр. |

Пауза — отдельное состояние сессии, не синоним закрытого сбора или закрытого лобби. Во время паузы часы и прогресс не меняются, применение запрещено; просмотр и локальные черновики доступны. Изменение паузы инвалидирует старый предпросмотр. Права/членство могут изменяться независимо, но каждый игровой запрос проверяет их заново.

Для раннего блока необходимы проверки паузы и модели продолжения; полноценные элементы управления паузой/возвращением завершаются R04. Пока точный порядок правок на паузе не определён, разрешать только явно предусмотренные операции мастера, без обхода через общий редактор мира.

**Инварианты:** один активный сбор; одно применение его версии в текущей линии истории; нет повторного открытия уже исполненного сбора обычной командой; новый сбор не уничтожает переносимую работу. Архивирование/отмена без исполнения также не отменяют прежний заряд автоматически.

## 3. Какие данные разделяем

| Логическая запись | Содержание | Хранение/доступ |
| --- | --- | --- |
| `RoundBase` | ID лобби, поколение восстановления, серверная ревизия, ID/эпоха сбора, версии заявлений, контрольные отметки управления, версия правил. | Сервер формирует сам; клиент не задаёт доверенную базу. |
| `RoundInput` | Текущие заявления, заданные бюджеты/стоимости, продолжения, отмены и решения мастера. | Проверяется относительно базы; публичные цели разрешает сервер. |
| `RoundPreview` | База, отпечаток ввода, точные события, последствия, блокеры, прогресс до/после, проверяемая ссылка на расчёт. | Только мастер/помощник с `rounds` и `viewSecrets`. До применения не меняет игровой мир. |
| `RoundProgress` | Устойчивый ID работы, герой, снимок действия/версии способности, исходная стоимость, точный остаток, стадия и происхождение. | Игровое состояние, входит в сохранение/копии; игроку только его проекция. |
| `RoundEvent` | ID события и раунда, игровое время, инициатор, категория, основание, изменения и зависимости, случайные результаты. | Сохраняется при применении; полный результат не рассылается всем. |
| `RoundReceipt` | Ключ команды, автор, отпечаток запроса, поколение истории, ID применения и итоговая ревизия. | Операционная запись сервера; не импортируется из пользовательской копии как разрешение на действие. |
| `BeforeState` | Игровое состояние непосредственно перед применением, позволяющее будущий откат. | Сервер, ограниченный объём, секретный доступ. Не содержит снимков самого себя рекурсивно. |

Это имена контрактов, не выбранная SQL-схема. При реализации выбрать долговременное хранение событий/снимков/квитанций в существующем сервере; одной памяти процесса недостаточно. Связанные записи сохраняются в одной транзакции с миром. Новые записи не требуют отдельного платного сервиса.

Права, членство, добровольное согласие передачи героя и журнал контроля остаются действующими серверными данными. Игровой снимок/импорт не предоставляет права и не возвращает старое согласие. Откат игровых часов не уменьшает серверные ревизии или поколение истории.

Полный снимок не вкладывать в `Campaign` вместе с предыдущими полными снимками: это создаёт рекурсивный рост. Историю/снимки хранить отдельно от текущего мира; в игровом состоянии — только нужные ссылки и текущий прогресс. Перед записью проверять совокупные лимиты, без молчаливого удаления истории. Число/размер сохранённых точек определить в R01 до добавления записи.

## 4. Время и перенос работы

Сохранить точный расчёт P11: мировая длительность действия = длительность раунда × личная стоимость / личный бюджет. «Ждать» использует мировые секунды и не ускоряется личным темпом. Зависимость бюджета от характеристик не вводить: текущие значения задаёт мастер явно.

Остаток хранить точной дробью, а не отображаемым процентом или округлённым числом. Числитель/знаменатель в JSON — строки; знаменатель положительный, дробь сокращена. Добавить проверки длины чисел/сложности расчёта, чтобы допустимый по размеру файл не создавал неограниченную работу.

Два разных вида прогресса:

- Для работы с личной стоимостью сохраняется остаток личной работы. При новом бюджете пересчитывается мировое время этого остатка, а не уже выполненная часть.
- Для ожидания сохраняется остаток мирового времени. Смена личного бюджета не сокращает ожидание.

Продолжение имеет прежний устойчивый ID; новый сбор не должен заново списать начальный расход или создать второе применение способности. Продолжение/отмена/замена работы выражаются явно, а не распознаются по похожему тексту или индексу в новой последовательности.

Прогресс фактически продвигается только при применении. Несколько предпросмотров, пауза, закрытие приёма и повтор HTTP-запроса не добавляют работы. Если отсутствует заявление или решение о продолжении, расчёт показывает вопрос мастеру, а не самостоятельно продолжает или отменяет действие.

Следующие действия очереди не начинают выполняться раньше завершения предыдущего. Их содержание сохраняется для проверки, но автоматическая повторная отправка на следующий раунд не предполагается. Выбор продолжения очереди — явный элемент нового плана/решения мастера; точный UX определить перед кодом формы.

Учебный пример из P20: длительность 5 с, бюджет 5000 личных мс, подготовка 8000 личных мс. После применения первого раунда остаётся 3000 личных мс; после следующего — готовый заряд, который выпускается отдельным действием. Это иллюстрация, не каноническая калибровка скорости.

## 5. Исполнитель и существующий движок

Нужна чистая функция `calculateRound(baseWorld, input, decisions, randomSource)`: не мутирует исходник, не вызывает сеть/БД и не получает случайность из `Math.random` неявно. Возвращает проверенный кандидат состояния и события либо блокеры. Для обучения та же функция позже работает с отдельной копией мира.

1. Проверить мир, сцену, участников, заявления, продолжения и разрешённые параметры.
2. Получить порядок с точными временами; выделить совпадения и неизвестные условия.
3. Обработать события последовательно на рабочей копии. После каждого события проверить изменившиеся цели, позиции, ресурсы и условия последующих действий.
4. Продвигать общие часы по границам событий; применить прежние процессы тела/поддержания в корректных интервалах. Два героя не продвигают мировые часы дважды.
5. Завершить оставшийся интервал раунда, сформировать переносимую работу и события; проверить итоговую схему и размер.
6. Показать мастеру результат и блокеры. Ни один неразрешённый блокер не допускает применение всего раунда.

Существующий `advanceWorld` работает с числом секунд. Преобразование точного времени для прежнего движка — отдельная граница адаптера: не использовать отображаемое округление, отклонять непредставимое/слишком малое продвижение до применения и сохранять исходное точное время в событии. Не менять порядок событий из-за численного допуска старого движка. Поддерживаемый диапазон/точность проверить сценариями до реализации.

Не применять весь раунд как независимые результаты от одного первоначального мира: раннее событие может изменить условия позднего. Перед расчётом не списывать ресурсы; при применении не пересчитывать заново случайный результат. Перенос работы не должен одновременно продвигаться собственным механизмом и второй раз через старый `Cast.readyAt`.

Для совпадающих действий мастер выбирает допустимый способ разрешения. Пока не утверждена модель одновременных взаимозависимых последствий, совпадение с конфликтом остаётся блокером. Порядок массива, ID героя и скорость ответа сети не служат игровым правилом. Выбранный порядок/способ входит во ввод, предпросмотр и историю.

| Категория | Первый поддерживаемый путь | Граница автоматизации |
| --- | --- | --- |
| Идти | Свободный маршрут X/Y/Z с проверкой границ, исходной позиции, опоры и доступности действия; время задаёт мастер. | Промежуточное положение на длинном пути, пересечение препятствий и смена опоры требуют явного правила/решения. Не выдавать полёт из одного значения Z и не заменять непрерывное движение скрытым телепортом. |
| Ждать | Мировой интервал, события тела/ресурсов в этом интервале, точный остаток ожидания. | Не использовать как автоматический ответ за отсутствующего игрока. |
| Взаимодействовать | Осмотр, открытие/закрытие существующего объекта с условиями и историей; остальные операции подключать явно. | Осмотр не раскрывает всю сцену автоматически; взять/активировать требует существующей модели содержимого/эффекта. |
| Говорить | Сохранить временное событие и содержание в закрытой истории. | До P25 не публиковать игровой текст в общий чат. Это временный предел, а не завершённая игровая речь. |
| Использовать предмет | Доступные операции существующего инвентаря через адаптер, с проверкой количества/слота/условий. | Неподдерживаемый эффект требует явных последствий мастера; шаблон предмета не означает любую автоматическую физику. |
| Использовать способность | Адаптер к старому движку для поддерживаемых типов и стадий; остальное блокируется либо имеет проверенные последствия мастера. | Расширенные цели, удержание, прерывания и эффекты завершаются R03; прежнее правило расхода не становится общим правилом новых способностей. |

Для первого кода брать небольшой полностью поддержанный набор (ожидание и простые взаимодействия), затем подключать движение, предметы и способности. Обозначение категории в меню не является доказательством готовности её исполнения. До полноценного набора R02/R03 первый игровой тест не объявляется пройденным.

## 6. Контракт расчёта и применения

Не изменять смысл имеющегося `/declarations/preview`: это временной прогноз без записи. Для последствий добавить отдельный контракт. Предлагаемые имена:

| Запрос | Ввод | Ответ/эффект |
| --- | --- | --- |
| `POST /api/lobbies/:id/rounds/calculate` | Ожидаемая база, бюджеты/стоимости, продолжения, решения мастера. | Проверенный предпросмотр и проверяемая ссылка на расчёт; игровая ревизия не повышается. |
| `POST /api/lobbies/:id/rounds/apply` | Ссылка на расчёт, ожидаемая база, уникальный ключ применения. | Один переход мира, события, исходный снимок, квитанция и новая серверная ревизия. |
| `GET /api/lobbies/:id/rounds/current` | Текущий аккаунт и выбранный лобби. | Полная мастерская либо личная проекция; без чужих планов/скрытых ID. |

Клиент не отправляет доверенный итоговый `world`, готовые броски или утверждение «проверено». Возможные реализации ссылки на расчёт: сохраняемый сервером неизменяемый пакет либо подписанный сервером проверяемый пакет. В R01 выбрать один вариант с проверкой размера/срока действия/перезапуска. Игровой предпросмотр не должен записывать прогресс/часы даже при служебном хранении пакета.

Ключ повторяемости относится к одной намеренной команде, не к одной попытке сети. После потери ответа клиент повторяет тот же ключ и тот же ввод. Изменение расчёта требует нового ключа. Сервер сравнивает отпечаток всего нормализованного ввода, включая решения и случайные результаты.

Порядок обработки `apply` в одной транзакции:

1. Заблокировать лобби, затем заново прочитать членство и полномочия. Нужны `rounds` и `viewSecrets`; отдельные изменения вне поддерживаемых операций требуют своих прав.
2. Проверить поколение истории и ключ. При совпавшей прежней команде вернуть её квитанцию без записи мира, нового аудита и повторных событий; при другом вводе с тем же ключом — конфликт. Даже квитанция выдаётся только после проверки текущего доступа.
3. Для новой команды проверить паузу/закрытость лобби, ссылку расчёта и **полную базу**: серверную ревизию, сбор/эпоху, версии заявлений, допуск и управление, правила.
4. Проверить, что сбор не исполнен, блокеров нет, кандидат и все ссылки/размеры допустимы. Зафиксировать исходный снимок до изменения.
5. Записать мир, переносимую работу, события, отметку исполнения, квитанцию и аудит. Повысить серверную ревизию ровно один раз.
6. После успешного commit отправить уведомление о новой версии. Сбой уведомления не отменяет выполненную операцию: клиент может прочитать состояние и повторить тот же ключ.

При сбое аудита, снимка, события, квитанции или записи мира откатывается вся транзакция. Одновременные применения одного или разных предпросмотров допускают ровно одного победителя; второе получает прежнюю квитанцию или конфликт.

`lobbies.revision` и `campaign.revision` — разные счётчики. Первый определяет конкурентную запись серверного мира; второй используется прежним движком. Не подменять один другим. Серверные операции восстановления повышают ревизию и поколение; старый расчёт не оживает, даже если восстановлен тот же игровой JSON.

Возврат квитанции после более поздних изменений не означает «мир сейчас равен результату этой команды»: ответ содержит ID применения и его ревизию; интерфейс отдельно загружает текущую версию.

## 7. Случайность и исходные снимки

Для расчёта сервер определяет воспроизводимый источник случайности, связанный с раундом и устойчивыми ID событий. Полученные значения входят в пакет предпросмотра; применение использует именно их. Клиент не выбирает удобный seed/бросок самостоятельно.

Повтор расчёта неизменного игрового ввода не должен скрыто давать новый бросок. Для переигровки R04 по умолчанию сохраняются прежние значения; намеренный новый бросок фиксируется отдельным решением мастера. Идентичность события после правки заявления определить до включения случайных эффектов в первый набор — не привязывать только к индексу массива.

`BeforeState` сохраняет игровые данные, нужные для обратного восстановления: герои/тело/ресурсы/касты, сцены/позиции/опоры, знания, инвентарь, шаблоны, время, заявления и переносимую работу. Операционные квитанции, поколения, права и серверный аудит не откатываются вместе с ним. Полноценный откат журнала раскрытий/речи остаётся O07; уже услышанное человеком технически не отменить.

## 8. Приватность, интерфейс и старые записи

- Сервер выдаёт игроку только собственную работу/заявление и последствия, доступные его знаниям. Остаток времени другого героя, скрытый NPC, исходный снимок и закрытый текст речи не попадают в ответ.
- Смена аккаунта/лобби/прав немедленно скрывает старый результат. Запрос отменяется; поздний ответ проверяется по контексту перед показом. Черновик привязан к аккаунту, лобби, сбору и герою; не очищается до подтверждённого результата.
- Во время применения кнопка защищена от повторного нажатия, но серверная повторяемость обязательна независимо от UI. При неизвестном исходе сети не объявлять ошибку исполнения окончательной; сверить квитанцию/текущее состояние.
- Открытые блокеры показываются мастеру с причиной и связанным действием. Недоступное игроку объяснение заменяется допустимой проекцией, без раскрытия секретной цели/преграды.
- Старые кампании без новых полей остаются валидными. Новые поля добавляются в схему, копирование, размерные проверки, импорт/экспорт и личную проекцию одновременно.
- Общий `PUT /world`, редактор сцен, удаление героя/сцены и восстановление копии должны учитывать активную работу и исполнение. Старый клиент не должен стереть новые состояния; отдельные команды не обходят паузу или отметку уже исполненного сбора.
- Импорт переносит игровые данные, но назначает новое поколение сервера и новые активные идентификаторы, где требуется. Служебные ссылки на предпросмотр и квитанции не считаются переносимыми полномочиями.
- Текущий предел мира 8 МиБ и импорта 10 МиБ сохранять до явного решения. Дополнительные серверные снимки получают отдельный ограниченный бюджет; нет обещания бесконечного бесплатного хранения.

## 10. Сценарии приёмки блока

| ID | Проверка | Ожидаемый результат |
| --- | --- | --- |
| R02-01 | Рассчитать два плана с разным темпом. | Точный порядок по заданным условиям; исходный мир неизменён. |
| R02-02 | Закрыть сбор, выполнить несколько расчётов, применить один. | Только применение меняет мир и часы; одна серверная ревизия. |
| R02-03 | Работа 8 с в двух раундах по 5 с; сменить личный бюджет. | Точный остаток, сохранение ID, без повторного начального расхода; готовность отдельно от выпуска. |
| R02-04 | Долгое ожидание при разных бюджетах. | Остаток в мировом времени; ускорение героя не сокращает ожидание. |
| R02-05 | Изменить цель/объект ранним событием. | Позднее действие проверяется по новому состоянию; нет применения невозможного результата. |
| R02-06 | Конфликт одинакового времени или отсутствующее заявление. | Вопрос мастеру; без неявного порядка/таймаута/штрафа. |
| R02-07 | Повторить ключ после потери ответа/перезапуска сервера. | Прежняя квитанция; ни второго расхода, ни новой записи события. |
| R02-08 | Тот же ключ, другой ввод; два одновременных применения. | Конфликт либо одна ранее выполненная команда; только одна запись мира. |
| R02-09 | Ошибка аудита/снимка/квитанции после подготовки изменения. | Полный откат всех записей. |
| R02-10 | Сменить сбор, восстановить копию, вернуть управление, отозвать права. | Старый расчёт отклонён; секретный ответ не возвращается. |
| R02-11 | Пауза, выход/возвращение, применение старого результата. | Нет продвижения на паузе; работа восстановлена; старый результат требует пересчёта. |
| R02-12 | Посмотреть API/уведомления разных игроков. | Только свои прогресс/планы и доступные последствия; нет чужих ID/заряда/закрытых слов. |
| R02-13 | Старый экспорт и новый экспорт с работой/связями. | Совместимость и полная игровая копия; повреждённый файл не записывается частично. |
| R02-14 | Поздний ответ после смены аккаунта/лобби; потеря сети при применении. | Черновик не потерян, другой контекст не подменён; исход определяется квитанцией. |
| R02-15 | Проверить малые/большие дробные интервалы и границу раунда. | Нет изменения порядка при округлении, двойного продвижения часов или скрытой потери работы. |
| R02-16 | Удаление занятой опоры, движение в воздухе, неподдерживаемый предмет/эффект. | Явный отказ/блокер или проверенное решение мастера, без придуманной механики. |

Проверки распределяются между чистым движком, UI и сервером SQLite/PostgreSQL. Общий инструмент проверяет завершённость TAP-наборов, lint и сборку. После реализации нужны мастер + два игрока в независимых браузерных сессиях, настоящий телефон и WebGL. Старый результат тестов не записывать как результат этого блока.

## 11. Оставшиеся решения перед конкретными операциями

Не требуется заново утверждать имя, канон, шесть действий, свободные координаты, портреты, передачу героя и перенос работы. Перед поддержкой соответствующей механики необходимо определить:

- O01/O04: разрешение взаимозависимых совпадений; в первом наборе допустимо требовать явное решение мастера. Автоматическую формулу характеристик не добавлять.
- O02: как маршрут даёт промежуточное положение/опору при незавершённом движении; какие столкновения проверяются автоматически, какие подтверждает мастер.
- O05: расход, удержание, выпуск, изменение цели и прерывание конкретной способности. Согласованный принцип не заменяет отсутствующие поля/правила.
- O07: идентичность бросков после изменения действия и граница будущего отката знаний.
- O10: бюджет хранения снимков/квитанций/истории и выбранный контракт долговременного предпросмотра.

Технические контракты можно реализовывать без введения канонических чисел. Нерешённая игровая операция остаётся явно неподдерживаемой/заблокированной до решения, а не получает произвольное правило. Следующий связный кодовый этап — форматы и проверки R01, затем серверное исполнение первого поддержанного набора R02 с транзакционными сценариями.
