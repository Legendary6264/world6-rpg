Сначала восстановить P11–P21, затем перенести этот отдельный коммит/патч с разрешением конфликтов в App, тестовом загрузчике и документации. Повторить проверки уже объединённого результата. Не заменять актуальный проект целиком этой рабочей копией.

## Подготовленные изменения

- Название «Грани Бытия» используется в основном меню, подвале, сообществе, заголовке редактора персонажей, входе, новостях и вкладке браузера. Название мира в лоре и магическом атласе остаётся «Мир 6».
- Общие название, описание и предложенный slug вынесены в `src/productBrand.ts`. Добавлен компактный SVG-знак с пиксельными гранями; он используется в меню, на главной и как favicon.
- Vite формирует description, application-name, theme-color и OG-метаданные. `VITE_SITE_URL` необязателен: без выбранного адреса canonical и `og:url` не добавляются. Подпуть GitHub Pages сохраняется; конечный `/` нормализуется.
- Публичные `VITE_SITE_URL`/`VITE_API_URL` проверяются при загрузке конфигурации. Неверный протокол, удалённый HTTP, wildcard, логин/пароль, query/hash и путь `/api` у адреса API отклоняются. Сообщение не выводит исходный URL с возможным секретом. Клиент нормализует внешние пробелы и конечный слеш адреса API.
- Новые TOTP-факторы получают friendlyName «Грани Бытия». Существующие подтверждённые факторы используются как раньше; автоматического удаления или пересоздания нет. URL регистрации/восстановления и права не изменены.
- Добавлены `.env.example`, необязательная переменная GitHub Pages `VITE_SITE_URL` и отдельный пример `deploy/render-frontend.example.yaml`. Основной `render.yaml` с API не меняется. В примере автоматическое обновление отключено, заданы Node 24, сборка/каталог и публичные настройки.

Ключи localStorage/черновиков, форматы архивов, имена таблиц/схемы `world6`, ID игровых сущностей, игровые формулы, 3D и API сохранены. Старые выгрузки продолжают импортироваться; новый бренд не требует миграции данных.

## Адрес и порядок перехода — пока проект решения O11

`grani-bytiya` остаётся предложенным slug. Доступность и конкретный публичный адрес не проверялись и не согласованы. Никаких редиректов на несуществующий адрес в клиенте нет.

| Настройка | Что подготовить перед переносом |
| --- | --- |
| Текущий фронтенд | По конфигурации проекта — `https://legendary6264.github.io/world6-rpg/`; сохранить доступ на время перехода. |
| Новый фронтенд | Подтвердить фактический адрес нового статического сайта. Сборка `npm ci --include=dev && npm run build`, каталог `dist`. |
| `VITE_API_URL` | Сохранить действующий origin API; по конфигурации проекта `https://world6-api.onrender.com`, без `/api`. Не переименовывать API вместе с продуктом. |
| `VITE_SITE_URL` | Точный выбранный основной адрес, включая подпуть при его наличии. Используется только для метаданных; не выбирает адрес входа или приглашения. |
| API `CLIENT_ORIGINS` | Добавить новый точный origin и на время перехода оставить старый `https://legendary6264.github.io`. Origin не содержит `/world6-rpg/`. |
| Supabase URL Configuration | Новый Site URL и точные разрешённые callback URL нового и старого фронтендов. Код возвращает регистрацию/восстановление на текущий адрес приложения. Проверить фактические письма и шаблоны. |

Проверенные документационные основания: [Render Static Sites](https://render.com/docs/static-sites), [схема Blueprint](https://render.com/schema/render.yaml.json), [Supabase Redirect URLs](https://supabase.com/docs/guides/auth/redirect-urls), [TOTP enroll](https://supabase.com/docs/reference/javascript/auth-mfa-enroll), [Vite Plugin API](https://vite.dev/guide/api-plugin.html).

Переход на другой origin требует нового входа; браузерные черновики и локальные листы сами между доменами не переносятся. Перед переходом скачать имеющиеся выгрузки персонажей/кампаний на старом сайте. Рабочие копии лобби сохраняются в той же серверной базе. Для полей, у которых нет экспорта, завершить работу или сохранить текст отдельно; общий архив не обещает включать каждую локальную форму. После импорта сверить список героев/кампаний.

Старые приглашения продолжают работать, пока старый фронтенд обслуживается тем же API. Новые приглашения создаются с адреса нового фронтенда с прежним кодом лобби. Сначала проверить вход, email, TOTP, приглашения, Socket.IO, права и черновики на обоих адресах. Автоматический перенос старых ссылок и токенов между доменами не реализован; способ будущего вывода старого адреса из использования остаётся O11.
