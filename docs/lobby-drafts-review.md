# Исправления архитектурного аудита «Мира 6»: A1–A7

Изменения устраняют потерю черновиков, смешение лобби при задержках API,
превышение допустимого размера кампании, гонки административных изменений,
потерю владельцев при восстановлении, конфликт после удаления облачного героя
и остановку уведомлений после временного сбоя проверки сессии.

Подготовлено для просмотра в отдельной ветке и черновике PR №1. Слияние с main
и публикация на рабочий сайт не выполнялись. Новые платные сервисы, фоновые
процессы, производственные зависимости и изменения схемы БД не нужны.

## Поведение после исправлений

| Аудит | Исправление | Что учитывать |
| --- | --- | --- |
| A1 | Черновики сохраняются в браузере отдельно по аккаунту и лобби, включая исходную серверную версию и незавершённые поля. Навигация, обновление токена и временная ошибка API сохраняют работу. | Участники видят изменения после отдельной публикации. При недоступном хранилище появляется предупреждение; копия в памяти живёт до закрытия страницы. |
| A2 | Один бюджет кампании — 8 МиБ — проверяется перед добавлением героя, публикацией и экспортом. Отказ на сервере не меняет мир, владельцев и версию. Экспорт использует компактный JSON. | В пределах HTTP/импорта 10 МиБ остаётся место для заголовка и владельцев. Лимиты отдельных героев и игровые расчёты сохранены. |
| A3 | Изменение роли и блокировки выполняется в одной транзакции с записью аудита. Действующий инициатор и адресат блокируются в стабильном порядке; права проверяются по свежим строкам. UPDATE меняет только переданные поля. | Администратор не может заблокировать уже назначенного администратора; блокировка не затирает параллельно назначенную роль. |
| A4 | Новый JSON лобби содержит опубликованный мир, владельцев и признаки одобрения героев. Восстановление заменяет мир и связи атомарно, с проверкой текущей версии. | Каждый владелец должен быть действующим участником целевого лобби. Для старых копий без владельцев их требуется назначить явно; неизвестный владелец автоматически ГМ не становится. |
| A5 | После успешного удаления героя из облака удаляется запомненная версия. Повторная загрузка передаёт версию создания −1. | Проверка конфликтов при обычном обновлении остаётся. |
| A6 | После серверного отключения Socket.IO клиент проверяет сессию через HTTP и повторяет временные ошибки с увеличением интервала до 30 секунд. Восстановленное соединение заново подписывается на лобби. | Отозванная/заблокированная сессия и требование второго фактора прекращают попытки. Поздний ответ после выхода из аккаунта не подключает прежний клиент. |
| A7 | Редактор имеет ключ аккаунт/лобби. Загрузка отменяется при уходе, а поздние ответы и чтение файла дополнительно проверяют жизненный цикл. Публикация использует лобби исходного черновика. | Ответ публикации обновляет только его версию и сохраняет изменения, сделанные во время запроса. |

Копия лобби сохраняет листы, общий каталог, часы и владельцев героев. Она не является
копией базы сайта: аккаунты, состав участников, чат и обращения поддержки не входят
в файл. Для переноса нужно сначала добавить владельцев в целевое лобби.

В сетевом редакторе прежнее восстановление без владельцев заменено новым процессом
с явным сопоставлением участников. В отдельном локальном редакторе прежнее
восстановление кампании остаётся доступным. Экспорт текущего черновика также
сохранён отдельно от копии опубликованного лобби.

## Состав изменений

- `LobbyCampaignEditor`, `lobbyDraftStorage`, `LobbiesPanel`, `onlineHooks`:
  принадлежность черновика, сохранение и защита асинхронных ответов.
- `campaignLimits`, `validation`, `lobbies`, `CampaignPanel`: единый бюджет мира,
  проверка до записи и экспорт без лишнего увеличения JSON.
- `community`: административная транзакция и проверка актуальных прав.
- `lobbyBackup`, `LobbyBackupPanel`, `lobbies`: формат копии, выбор владельцев,
  атомарный экспорт и восстановление.
- `CloudLibraryPanel`: очистка версии после успешного удаления.
- `socketRecovery`, `OnlineProvider`, `app`, `auth`: восстановление уведомлений
  и различение временной недоступности проверки сессии и отозванного доступа.
- UI- и серверные регрессионные проверки; UI-шаг существующего CI.

Изменения `CharacterManager` и `CampaignPanel` касаются сохранения, передачи снимка
и интерфейса восстановления. Движок правил, схемы игрового канона, анатомия,
формулы, тексты мира, 3D-компоненты и графические ресурсы не менялись.

## Автоматическая проверка

- `npm run test:ui`: 16 проверок React DOM/jsdom. Используются настоящие панели,
  редактор, хуки, формат копий и хранилища; ответы API управляются, визуальные
  дочерние компоненты заменены для проверки без WebGL.
- `npm test`: 44 игровых сценария.
- `npm run test:server`: 49 проверок, включая SQLite и PostgreSQL/PGlite,
  конкурентные административные запросы, размер мира, перенос владельцев,
  откат транзакций и настоящие локальные соединения Socket.IO.
- В проверках Supabase используются локальные ответы Auth: временный сбой
  возвращает 503, сбой чтения auth.sessions не считается отзывом сессии,
  отозванная сессия возвращает 401. Рабочая база не изменялась.
- `npm run build`: успешно.
- `npm run lint`: успешно; 12 существующих предупреждений, новых нет.

Тестовая зависимость jsdom добавлена только для разработки. Проверка `npm audit`
при её добавлении показала 0 известных уязвимостей; последующие A2–A6 зависимостей
не добавляли. Это не заменяет отдельную проверку безопасности всего проекта.

## Ручная проверка перед публикацией

1. Изменить героя ГМ без публикации, перейти в другой раздел и вернуться;
   переключить лобби и аккаунт. Каждый черновик должен остаться у своего владельца.
2. Задержать загрузку лобби A, открыть B; ответ A не должен появиться в B.
3. Из второго клиента изменить серверный мир: публикация прежнего черновика
   должна получить конфликт и сохранить локальную работу.
4. Скачать копию лобби с героем друга, добавить друга в другое лобби и восстановить.
   Проверить доступ друга к своему герою; у старого JSON назначить владельца явно.
5. Удалить облачного героя и загрузить его заново из локальных листов.
6. При временной недоступности API проверить восстановление уведомлений,
   затем выход из аккаунта и запрет переподключения отозванной сессии.
7. Проверить MFA в настоящем облачном аккаунте, открытие 3D и игровой сценарий
   в браузере. Эти проверки с рабочим Supabase и WebGL ещё не выполнялись.
