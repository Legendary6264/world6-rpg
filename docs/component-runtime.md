# Компоненты и единая граница записи мира

Статус: этапы 2–3 реализованы в ветке PR №6. Добавлено совместимое постоянное хранение; рабочая БД не изменена. Старый JSON остаётся авторитетным форматом на время перехода.

## Модель

`EntitySnapshot` имеет версию формата и ревизию мира. Каждый компонент имеет собственную версию. Снимок содержит:

- Сущности персонажей: идентификация/профиль, атрибуты, ресурсы, развитие, знания, анатомия, правила RPG и необязательная позиция с опорой.
- Сущности сцен: параметры сцены и явный порядок объектов и токенов.
- Сущности объектов: идентификация, XYZ и сцена, геометрия, физические флаги, оформление.
- Компонент общей кампании и порядок персонажей/сцен.

ID сущности кодируется JSON-массивом типа и исходных ID. У объекта в ключ входит сцена: одинаковые локальные ID в двух сценах не конфликтуют. Порядок массива сущностей может меняться, порядок игрового содержимого сохраняется отдельными связями.

`projectWorldEntities` и `restoreWorldEntities` образуют обратимый адаптер. Он не исполняет действий, не меняет игровое время, ресурсы или управление. Незнакомые версии компонентов, лишние компоненты и разорванные связи отклоняются. Дополнительные поля прежних объектов и персонажей помещаются в версионированный `extensions`; при восстановлении они не могут переопределить известные поля.

Геометрия мастера использует `objectEntity`. Геометрия игрока по-прежнему строится только из раскрытой сервером карты. Полный снимок сущностей никогда не используется как источник личного обзора.

## Координатор

`commitWorld(tx, lobby, candidate, options)` — единственное место обновления текущего `world_json`. Создание новой кампании остаётся существующей атомарной операцией INSERT.

Последовательность записи:

1. Серверный модуль проверяет текущие права, статус кампании, ревизию и предметные условия внутри транзакции с блокировкой лобби.
2. Координатор валидирует мир существующими правилами.
3. Создаёт компонентные снимки до и после команды и проверяет точное восстановление валидированного мира из новых компонентов.
4. Формирует дельту: какие сущности и компоненты созданы, изменены или удалены. Сравнение игнорирует порядок ключей объектов, сохраняя значимость порядка массивов.
5. Записывает исходный JSON команды, следующую ревизию и время только при совпадении ожидаемой ревизии. Изменение ревизии допускается ровно на один шаг.
6. В той же транзакции координатор сохраняет компоненты и событие. Для ещё не перенесённой кампании сначала сохраняет базовый снимок предыдущего мира. Вызывающий модуль завершает запись аудита, квитанций, истории и других данных. При ошибке откатывается всё.
7. После успешного завершения транзакции существующий маршрут посылает обычное уведомление об изменении лобби.

Координатор намеренно не открывает самостоятельную транзакцию и не выдаёт права. Его вызывают только серверные модули внутри уже проверенного контекста. Существующие ключи повторов, поколения истории и квитанции раундов сохраняются; новый независимый механизм повторного исполнения не вводится.

Через него проходят сцены, запуск сцены, публикация/восстановление мира, присоединение персонажа и удаление участника, рассмотрение героя, NPC, раскрытие и заметки, заявления, применение/откат раунда, импорт/очистка истории, справочник и операции имущества/экономики.

## Чтение, история и доступ

`GET /api/lobbies/:id/entities` отдаёт полный снимок только после проверки членства и `viewSecrets` в той же транзакции. Снимок содержит секретные знания и анатомию; открытого и игрового варианта этого API нет. Для игрока используется прежний адрес личного восприятия с проверкой владельца/контроллера.

После переноса снимок читается из отдельных таблиц и сверяется с авторитетным JSON: SHA-256 исходных байтов, поддерживаемая версия схемы, обратимость и равенство валидированному миру. Несовпадение возвращает 409; молчаливого исправления или выбора одной из расходящихся копий нет. До переноса снимок строится в памяти, чтение не создаёт строк в новых таблицах.

Команды изменения прав могут увеличить общую ревизию без изменения мира. Хранимая ревизия компонентов остаётся ревизией последней записи мира, API возвращает актуальную ревизию конкурентного доступа. Следующее событие соединяет две сохранённые ревизии, допуская такой пропуск.

Валидация может нормализовать старый формат для внутренней работы. Чтение компонентов не записывает такую нормализацию обратно. Координатор сохраняет исходную строку текущего мира, если получил строку, и не изменяет исторические снимки. Объектные входы сериализуются обычным способом. Проверка обратимости сравнивает восстановленный снимок с валидированным миром.

## Постоянное хранение

Добавочные миграции `014-components-postgres.sql` и `014-components-sqlite.sql` выполняются существующим серверным механизмом схем. Это не миграции Supabase CLI; live SQL в Supabase не применялся. Запуск сервера создаёт пустые таблицы, без массового обхода кампаний.

| Таблица | Назначение |
| --- | --- |
| `world_component_heads` | Версия схемы, ревизия записи мира, хеш исходника, маркер исполнителя раундов, корневые компоненты и счётчик объёма журнала |
| `world_entities` | Составной ID сущности, тип и порядок |
| `world_components` | Составной ключ кампании/сущности/компонента, версия и данные |
| `world_component_events` | Базовый снимок и последующие дельты с результатами, без повторного исполнения правил |

PostgreSQL использует JSONB для данных компонентов, корневой информации и событий; SQLite — текст JSON. Тип, версия, ключи, порядок, связи и ревизии имеют отдельные типизированные колонки и ограничения. Первичные/уникальные индексы начинаются с внешних ключей кампании/сущности. В PostgreSQL таблицы находятся в закрытой схеме `world6`, с RLS и отозванными правами PUBLIC. Доступ идёт через серверные проверки, схема не предназначена для клиентского Data API.

Обычная команда обновляет только изменённые компоненты. Смена состава или порядка сущностей пересоздаёт их текущую проекцию; журнал от этого не меняется. Вставки выполняются ограниченными пакетами по 100 строк, чтобы избежать запроса на каждый компонент и переполнения числа параметров.

## Перенос отдельной кампании

| API | Поведение | Доступ |
| --- | --- | --- |
| `GET /api/lobbies/:id/entities` | Текущий проверенный снимок, без записи | `viewSecrets` |
| `GET /api/lobbies/:id/entities/storage` | Режим legacy/dual-write, обе ревизии, число сущностей, объём и лимит журнала; одновременно проверяет совместимость | `viewSecrets` |
| `POST /api/lobbies/:id/entities/migrate` | Тело `{revision}`; перенос одной кампании без изменения игрового времени или ревизии. Повтор возвращает `migrated:false` | Только главный ГМ |
| `GET /api/lobbies/:id/entities/archive` | Исходный текущий JSON, снимок и полный компонентный журнал; перед выгрузкой проверяет восстановление | `viewSecrets` |

При первой обычной записи мира перенос также выполняется автоматически в общей транзакции. Отдельная команда нужна для предварительной проверки и переноса выбранной копии. Проверки доступа и блокировка кампании предшествуют чтению/записи. Повтор переноса не дублирует аудит или исходник. Отдельной панели миграции в интерфейсе пока нет.

Базовое событие сохраняет точную исходную строку, её SHA-256, нормализованный компонентный снимок, версию схемы и маркер исполнителя. Оно не меняет `world_json`, прежние раунды, контрольные точки или архивы. Последующие события хранят только изменённые компоненты и корневую информацию/порядок; это ещё не журнал всех предметных команд игры. Маркер `rulesVersion` соответствует `ROUND_EXECUTOR_VERSION`, он не обозначает новую версию канона.

`replayComponentEvents` восстанавливает снимок для любого сохранённого префикса журнала. Данные применяются без расчёта бросков, времени, ресурсов и новых правил. Переносы, удаления, необязательные компоненты и порядок восстанавливаются точно. Восстановление не публикуется в текущую кампанию автоматически.

Триггеры БД запрещают UPDATE/DELETE событий. Удаление возможно только каскадом при удалении самой кампании. Перезапуск, отмена раунда, восстановление мира и очистка старой игровой истории не переписывают компонентный журнал. Ограничение — 64 МиБ сериализованных полезных данных на кампанию: при достижении команда целиком отклоняется с 409. Удаления старых событий или автоматической ротации нет; счётчик не отражает физический размер JSONB/индексов. Защищённая выгрузка сохраняет историю, но сама не освобождает квоту.

## Проверка восстановления и границы перехода

Перед будущим развёртыванием: резервная копия БД, восстановление в изолированную среду, проверка GET storage, перенос выбранной копии, сравнение исходных байтов/компонентов, выгрузка архива и восстановление его журнала. На этом этапе ни данные, ни конфигурация рабочего сайта не менялись.

Старые архивы кампаний по-прежнему содержат прежние данные мира/раундов. При импорте в новую кампанию компонентный журнал начинается с нового базового снимка; полный прежний компонентный журнал сохраняется отдельно через `/entities/archive`. Ссылки/данные `artwork` переносятся без изменения. Новый бакет для крупных 3D-моделей, выгрузка тяжёлых вложений и управление жизненным циклом ресурсов ещё не реализованы; это остаётся открытой частью этапов 3/7.

Возврат компонентов в прежний мир проверяется адаптером и общими сценариями архивов/откатов. Для отката версии сервера с сохранением полной истории нужно восстановить согласованную резервную копию либо приостановить запись. Запуск старого сервера с записью в тот же JSON рассинхронизирует компоненты; при возврате новой версии такие данные намеренно блокируются для разбора на копии. Ручное удаление таблиц или обход журнала не является поддерживаемым способом отката.

Переход к компонентам как единственному источнику истины, отдельные типизированные SQL-таблицы для каждого семейства данных и версия 2 формата пока не вводятся.

## Проверки

В модульных сценариях проверяются точное восстановление, порядок, дробные высоты и опоры, стабильные ID, отсутствие общих изменяемых ссылок, неизвестные версии/компоненты, дубликаты, разорванные связи, расширения и дельты.

В интеграционных сценариях на SQLite и PostgreSQL проверяются доступ к полному снимку, гонка двух записей сцены, stale compare-and-swap, запрещённый скачок ревизии, откат при сбое аудита, сохранение точных байтов JSON и восстановление после перезапуска. Общие тесты дополнительно покрывают раунды, историю, копии, экономику, NPC и пять участников полигона.

Дополнительные интеграционные сценарии проверяют постоянные строки JSONB, исходный снимок и повтор переноса, отсутствие записи при GET, воспроизведение дельт, удаление/создание и порядок, пропуски ревизий управления, атомарность сбоев компонента и аудита, неизменяемость журнала, лимит, рассинхронизацию, изоляцию кампаний, защищённый архив и повторное открытие схемы. Проверки PostgreSQL используют PGlite; отдельный сетевой сервер PostgreSQL и рабочий Supabase этим прогоном не проверялись.

Итоговый прогон: 570 серверных проверок, 174 интерфейсных, `npm test`, клиентская сборка и линтер прошли. Новых предупреждений линтера нет; прежние предупреждения проекта сохраняются.
